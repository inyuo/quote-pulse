## 一、数据碰撞「数据服务连接失败」排查与服务恢复

**现象**：面板显示「数据服务连接失败 / 请确认数据服务地址可访问且服务已启动（8800 端口）」。

**排查**：不是插件配置问题，也不是服务端挂了整机。

- TCP `124.71.128.214:8800` 可连（0.001~0.007s），但 `/`、`/qp/status`、`/api/v1/health` 全部 `Empty reply from server`（HTTP 000，约 3s），原始 HTTP 请求直发也一个字节不回 → gunicorn **accept 后无响应**，单 worker 僵死。
- SSH 22 正常；`logs/gunicorn.log` 显示 `06:00:39 [INFO] Shutting down: Master`（旧 worker 被 SIGTERM 后未拉起），日志里还有大量公网开放代理探测（`GET http://azenv.net/`、`CONNECT api.ipinfo.io:443`），可能与 worker 被异常请求占住有关。
- 服务器内存 1837M 总量 / 634M 可用，未 OOM。
- 服务器上另有**另一个** gunicorn 实例绑定 `127.0.0.1:8050`（PID 23859，Nov10 起运行），`run.sh` 管的是 8800，排查时不要混淆/误杀。

**修复**：`cd /root/.hermes/invest-monitor && ./run.sh restart` → 新 PID 30888。重启后本机验证 `health 401`（0.04s）、`collision 401`、`root 302`，说明服务与全局鉴权恢复正常。

**SSH 连接要点**：`root@124.71.128.214` 需 `~/.ssh/huaweicloud_key`（`dev_key` / `id_ed25519` 未验证），首次连接因 known_hosts 缺条目报 `Host key verification failed`，本次已用 `StrictHostKeyChecking=accept-new` 加入主机密钥。命令示例：
```
ssh -o BatchMode=yes -o StrictHostKeyChecking=accept-new -i ~/.ssh/huaweicloud_key root@124.71.128.214
```
